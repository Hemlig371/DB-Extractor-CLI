# DB Extractor, сборка на Rust

Тот же интерфейс, что у Python-версии (`src-python`): флаги, аннотации `-- @DX_*`, формат `export_log.txt`, коды возврата `0/1/2`. Старые команды и SQL-файлы работают без изменений. Описание всех параметров: [основной README](../README.md).

Отличия от Python-версии:

| | Python | Rust |
|---|---|---|
| Память | результат запроса целиком в памяти | данные идут пакетами (`--batch-size`, по умолчанию 100 000 строк), на диск пишутся сразу |
| Запуск | PyInstaller-пакет, папка с библиотеками | один исполняемый файл |
| Источники | polars + connectorx из pip | connectorx 0.4.6, **все 11 источников собраны в бинарник**, выбор по схеме URI во время работы |
| `--cast-universal` | Decimal, Datetime, Categorical, Object, Int128 | то же, плюс вложенные типы (списки, структуры, map) как JSON-строки и любые неизвестные типы как строки |
| Новые параметры | `--hash-salt` | `--hash-salt`, `--batch-size` |

## Источники данных

Oracle, PostgreSQL, ClickHouse, MySQL/MariaDB, SQL Server/Azure SQL, SQLite, BigQuery, Trino, Redshift. Подключение только через URI (таблица с примерами в основном README). Пересобирать бинарник для другой БД из этого списка не нужно. Для Oracle на машине должен стоять Oracle Instant Client: бинарник запускается и без него, ошибка появится только при подключении к Oracle (с подсказкой, куда его положить). БД, которых нет в списке, выгружайте через DuckDB.

## Потоковая запись

Схема результата известна до чтения строк, поэтому все преобразования (`--hash-columns`, `--utc`, `--fill-nulls`, `--drop-nulls`, `--cast-universal`, `--categorize`) строятся по схеме один раз и применяются к каждому пакету. Это значит, что `--cast-universal` по типам не зависит от данных: каждый пакет получает одинаковые типы.

Что это даёт по памяти: пакетом называется `--batch-size` строк. Parquet дополнительно накапливает одну группу строк (262 144) перед записью. Важное ограничение: connectorx читает из БД в отдельных потоках и передаёт пакеты по неограниченной очереди. Если диск пишет медленнее, чем БД отдаёт, очередь растёт. Поэтому потоковая запись снижает пиковую память, но жёсткого предела не гарантирует. Жёсткий предел потребует правки connectorx (очередь с ограничением); это запланировано отдельным шагом.

Отличия поведения, вытекающие из потоковости:
- Сообщение `Extracted and processed N rows. Saving to ...` выводится после того, как все строки записаны, непосредственно перед финализацией файла.
- `--categorize` меняет только Parquet (словарное кодирование). В CSV, JSONL и Arrow значения и так строки. В Arrow IPC (файловый формат) словари с разным содержимым в разных пакетах не допускаются, поэтому категоризация там не применяется.
- Числа, даты и т. п. для `--hash-columns` переводятся в текст средствами Arrow, а не polars. Для строк и целых хеши совпадают с Python-версией; для дробных чисел, дат и временных меток текстовая форма может отличаться, и тогда хеши разойдутся. Для надёжного совпадения хешируйте колонки, приведённые к строке в SQL.

## Обработка ошибок и неподдерживаемые типы

connectorx сообщает о неподдержанных типах паникой (`unimplemented!`), а не обычной ошибкой. Бинарник перехватывает такие паники и превращает их в запись `ERROR` в журнале и сообщение с подсказкой: приведите колонку в самом SQL (`TO_CHAR(col)`, `CAST(col AS VARCHAR)`). Сюда относятся, например, Oracle `INTERVAL`, `ROWID`, `RAW`, `TIMESTAMP WITH LOCAL TIME ZONE` и PostgreSQL `interval`, `money`, `xml`.

## Сборка

```bash
cd src-rust
cargo build --release -p db-extractor
# результат: target/release/db-extractor
cargo test --workspace --release
```

Нужны Rust (stable), на Linux ещё `pkg-config` и `libssl-dev`; для сборки OpenSSL на Windows нужен Perl (есть в Git for Windows и Strawberry Perl). Первая сборка долгая (connectorx с десятью источниками), следующие используют кэш.

Структура:
- `dbx-core` : чистая логика без зависимостей (разбор SQL, аннотации, выбор формата и сжатия, сопоставление колонок, маскирование паролей, формат журнала). Тесты запускаются быстро: `cargo test -p dbx-core`.
- `db-extractor` : чтение (`extract`), преобразования (`transform`), запись (`writers`), запуск и журнал (`run`), командная строка (`cli`).

После первой успешной сборки закоммитьте `Cargo.lock`, чтобы версии зависимостей были зафиксированы (в репозитории его пока нет, потому что он создаётся при первой сборке).

## Сравнение с Python-версией

`tests/parity/run_parity.py` запускает обе версии на одной SQLite-базе по 25 сценариям (форматы, сжатие, хеши, заполнение и удаление NULL, UTC, универсальный каст, категоризация, партиции, пустой результат, ошибки, аннотации) и сравнивает коды возврата, записи журнала и содержимое файлов (имена колонок, семейства типов, значения). В CI это отдельный шаг на каждой ОС.

```bash
pip install -r requirements.txt
python tests/parity/run_parity.py --rust src-rust/target/release/db-extractor
```

Что в паритет не входит: Decimal и типы конкретных СУБД (SQLite их не имеет). Их проверяют модульные тесты `transform.rs`; для Oracle доступа нет, поэтому эталоном служит поведение Python-версии на тех же запросах.

## Известные ограничения и планы

- Сборка не проверялась на реальных Oracle, ClickHouse и PostgreSQL: в среде разработки не было доступа ни к базам, ни к crates.io. Проверка идёт в CI (модульные тесты, паритет на SQLite) и на вашей стороне.
- Форматы времени в CSV подобраны так, чтобы совпадать с polars (`2024-01-02T03:04:05.123456`, смещение `+0000`). Если паритет-проверка покажет расхождение, формат правится в `writers.rs` (две строки).
- Planned: локальная правка connectorx для типов Oracle, которые он не читает сейчас (`BOOLEAN`, `INTERVAL`, `TIMESTAMP WITH LOCAL TIME ZONE`, `ROWID`, `RAW`), и ограниченная очередь пакетов. Делается после первой зелёной сборки, потому что требует копии connectorx в репозитории.
